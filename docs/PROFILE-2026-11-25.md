# Phone profile, 2026-11-25: where the time goes, stutters, what to improve

Phantom Hourglass and Spirit Tracks, on the **Moto G Stylus 2025** (Snapdragon, 60 Hz panel in this test) and the
**Pixel 8** (Tensor G3, 120 Hz panel). Each game ran with its **clang** game module and its **TinyCC** one (the same
generated C, built by the two compilers), in four 30 s segments, each with another save spot and renderer.

## How it was measured
- Test apps: PH `com.phrecomp.ph.fastcc` (tag `fastcc-2`), ST `com.strecomp.st.fastcc` (0.2.0-fastcc), widescreen off.
- Each segment: the app force-stopped, the module, renderer settings and save state copied in, the game started from
  that state (Continue). **PH ran paced at 60 fps** (normal play, `bench_paced`); **ST ran unpaced** (its test app has no
  paced option yet), so ST's fps is "how fast it can go", capped at ~125 by the Pixel's 120 Hz screen.
- `simpleperf record --app` (cpu-clock, 1000 Hz, 26 s per segment): CPU time by thread, library and function.
- SurfaceFlinger `--timestats` for the game's layer: frames shown, average fps, and the time between frames shown.
  **Slow frames** = frames shown 25 ms or more after the one before (a missed refresh at 60 Hz: a visible stutter).
- CPU clocks, battery temperature and Android's thermal status every 5 s.
- Caveats: one run per cell (no repeats); in each pair clang ran first; the scenes are save spots with nobody playing
  (no input), so busy moments like boss fights or the sea are not covered.

### Where the CPU time goes (all segments, mean share of the app's CPU samples)

| Part | Moto PH | Moto ST | Pixel PH | Pixel ST |
|---|---:|---:|---:|---:|
| melonDS ARM7 (interpreted second CPU, its bus and timing) | 26% | 31% | 22% | 28% |
| Game code (recompiled ARM9; clang and TinyCC together) | 16% | 16% | 19% | 15% |
| Renderer (Compute / OpenGL / Software, 2D) | 9% | 10% | 11% | 10% |
| GPU driver | 7% | 8% | 11% | 11% |
| memcpy / malloc | 7% | 5% | 7% | 7% |
| DS 3D geometry (GPU3D) | 4% | 6% | 4% | 5% |
| DS timers / DMA / scheduler | 4% | 5% | 4% | 4% |
| Runtime glue (`ntr::RuntimeImpl::lookup`, `advance`, overlays) | 4% | 4% | 6% | 3% |
| Android / ART / binder | 9% | 4% | 7% | 3% |
| Audio (SPU) | 1% | 1% | 1% | 1% |

Threads: the game thread is 82% (PH) and 95% (ST) of the app's CPU. PH also spends 5-7% in `SDLThread` and 2-5% in
binder threads (Pixel / Moto), against 1-3% and 1-2.5% for ST.

Clocks and heat: the Moto stayed at 33-35 C, thermal status 0, top core 1.2-2.4 GHz. The Pixel reached thermal
status 1 (light throttling) within the first minutes at 36.5-37.9 C; its top core averaged ~1.9 GHz.

## What it shows
1. **clang is better, as it felt.** The clang module needs a third of TinyCC's CPU for the game's own code (5-11% of
   the app's CPU against 20-31%). On the Pixel (PH, paced) that halves the share of slow frames in every renderer
   (12-16% against 23-26%); on the Moto in Compute 2x it is 30% against 41% slow frames and no frame over 50 ms
   (TinyCC: 41). Unpaced ST is 15-27% faster with clang in the heavy renderers (Compute 2x/4x, Pixel Software).
   OpenGL and Software on the Moto were a tie or slightly better with TinyCC there (single runs). The earlier
   600-frame A/B (TESTED.md) saw no difference because those scenes left the CPU spare; under load it shows.
2. **The Moto cannot hold 60 fps in PH with the Compute renderer**: 47 fps at 2x, 36 at 4x, whatever the compiler;
   OpenGL 2x 55-56, Software 1x 60. The game's frames come out at 16 ms or 33 ms (missed refreshes), not in between.
   ST holds up better on the Moto (82 fps unpaced at Compute 2x), so PH's scene or PH's extra Android work costs more.
3. **The Pixel shows 61.7 fps but 12-26% of frames arrive late.** The game asks Android for 120 fps on its surface
   (timestats: `frameRate = 120.00` vote on both phones; the Moto's panel ran at 60 Hz anyway) while it makes 60: on the 120 Hz panel frames land at 16.7 or 25 ms
   (one refresh late) instead of every 16.7 ms. That is judder even when the average is fine.
4. **The emulated ARM7 is the biggest single cost** (22-31%): melonDS interprets the DS's second CPU (sound, touch,
   timers) instruction by instruction, plus its bus reads and cycle counting.
5. Smaller items: the runtime's function lookup (`ntr::RuntimeImpl::lookup` ~3%) and `advance` (~2%); memcpy and
   malloc/free 5-7% (allocations every frame); PH's Java/SDL side does more per frame than ST's.

## To improve (next week), most gain first
1. **Ship the clang build** (PR #24): measurably fewer slow frames, done.
2. **Frame pacing: ask Android for 60, not 120.** Set the game surface's frame rate to 60
   (`ANativeWindow_setFrameRate(..., 60, ANATIVEWINDOW_FRAME_RATE_COMPATIBILITY_FIXED_SOURCE)`, or SDL's hint if it has
   one) so 120 Hz phones show every frame for exactly two refreshes. Check with timestats: slow frames should drop to
   near 0 on the Pixel.
3. **Renderer default by phone**: the Moto (and phones like it) should start on OpenGL 2x, not Compute; or drop to
   OpenGL when the game misses 60 for a few seconds. Measure the GPU's load on the Moto at Compute 2x to confirm the
   GPU, not the CPU, is the limit there.
4. **ARM7 cost**: try melonDS's ARM JIT for the ARM7 on arm64 (if it builds for Android), idle-loop skipping for the
   ARM7's wait loops, or cheaper timing for the ARM7; each is a percentage of the whole frame.
5. **PH's extra Android work** (SDLThread + binder 6-12% against ST's 3-6%): find what PH's Java side does every frame
   (on-screen pad, FPS badge, vibration, sensors) with a call-graph profile (`simpleperf record -g`).
6. **Runtime lookup**: cache the target of indirect calls per call site (or direct calls where the target is known),
   to cut `lookup` + `advance` (~5%).
7. **Allocations per frame**: find the malloc/free/memcpy callers with `-g` and reuse buffers.
8. **Measure again** with repeats (3 per cell, alternating), ST's paced option, and a moving scene (an input script
   or a busier save spot), and both PH and ST at the same settings.

Raw data (per segment: simpleperf reports, timestats, clocks) stays on the test PC; the test apps and modules stay on
the phones under `/data/local/tmp`.
